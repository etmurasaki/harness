## Findings

1. **Perses Operator memory growth: 24Mi -> 217Mi (+193Mi)**: With a clean restart baseline of 24Mi, creating 800 PersesDashboard CRs caused perses-operator memory to grow by 193Mi to 217Mi. The 128Mi CSV request is exceeded by 89Mi (1.7x), but the pod remains within its 512Mi limit with 295Mi headroom.

2. **Memory leak confirmed: 87% of growth retained after deletion**: After deleting all 800 dashboards and waiting 60s, perses-operator memory dropped only 26Mi (from 217Mi to 191Mi), retaining 167Mi of the 193Mi growth. This is a **severe leak** -- 87% of allocated memory is never released. This definitively confirms the need for [perses-operator PR #414](https://github.com/perses/perses-operator/pull/414).

3. **Clean baseline eliminates noise**: Run 11 started at 185Mi residual and showed only 14Mi retained -- misleading because the leaked memory from the prior run was already included in the baseline. This clean-baseline run (24Mi) reveals the true scale of the leak.

4. **Perses server stable**: The perses-0 pod showed modest growth (88Mi) and minor recovery (84Mi after deletion, -4Mi). Memory is dominated by server runtime, not dashboard state.

5. **Observability Operator stable at 63Mi**: Well within its 256Mi request (25% utilization), unaffected by dashboard load.

6. **Comparison with Run 11 (residual baseline)**:

| Metric | Run 11 (185Mi baseline) | Run 12 (24Mi baseline) |
|---|---|---|
| Baseline | 185Mi (residual) | 24Mi (clean restart) |
| Post-creation | 344Mi | 217Mi |
| Post-deletion | 199Mi | 191Mi |
| Apparent growth | +159Mi | +193Mi |
| Apparent recovery | 145Mi (91%) | 26Mi (13%) |
| Actual leak | 14Mi | **167Mi** |

The Run 11 "91% recovery" was misleading -- the memory was already leaked from the prior run. With a clean baseline, only 13% of growth is recovered.
