## Findings

1. **Perses Operator memory growth confirmed at 800 dashboards**: Memory grew from 185Mi to 344Mi (+159Mi) after creating 800 PersesDashboard CRs. The 128Mi CSV request is exceeded, but the pod remains within its 512Mi limit with 168Mi headroom.

2. **Partial memory recovery after deletion (91%)**: After deleting all 800 dashboards and waiting 60s, perses-operator memory dropped from 344Mi to 199Mi — recovering 145Mi of the 159Mi growth. The 14Mi residual is consistent with the metrics leak described in [perses-operator PR #414](https://github.com/perses/perses-operator/pull/414).

3. **PR #414 relevance confirmed**: The residual 14Mi after deletion aligns with the PR's description of metrics objects not being cleaned up on resource deletion. The PR also adds client caching and status-update-only-on-change optimizations that should reduce the peak memory growth during dashboard creation.

4. **Elevated baseline (185Mi)**: The perses-operator was not restarted before this run, so the baseline includes residual memory from the prior run (Run 10, also 800 dashboards). A clean restart baseline is typically 19-52Mi.

5. **Perses server stable at 106Mi**: The perses-0 pod held steady at 106Mi before and after dashboard deletion, suggesting its memory is dominated by the server runtime rather than dashboard state.

6. **Memory scaling trend (all runs, pre-fix perses-operator)**:
