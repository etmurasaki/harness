## Findings

1. **Perses Operator OOMKill under dashboard load**: With 2000 PersesDashboard CRs across 100 namespaces, the perses-operator reached 492Mi memory usage and was OOMKilled twice. The 512Mi limit is insufficient for this workload. The memory request of 128Mi is also significantly undersized (actual usage is 3.8x the request).

2. **Perses Server memory growth**: The perses-0 StatefulSet pod grew from ~57Mi (no dashboards, previous run) to 269Mi with 2000 dashboards. No request/limit is declared for this pod, so it cannot OOMKill but also has no resource governance.

3. **Observability Operator stable**: Memory remained at 50Mi regardless of dashboard load, well within its 256Mi request and 512Mi limit.

4. **Monitoring Console Plugin minimal**: Only 8Mi memory usage.

The primary concern is the perses-operator pod hitting memory limits and OOMKilling under a 2000-dashboard workload. The 512Mi limit (set per COO-1014) is not sufficient when managing a large number of PersesDashboard CRs.

### Key Observation: Possible Memory Leak

The perses-operator does not fully release memory after PersesDashboard CRs are deleted. Between Run 2 and Run 3:

- Run 2 cleanup deleted all 2000 dashboards and 100 namespaces
- Run 3 baseline showed the perses-operator still at **431Mi** (vs 24Mi on a fresh start)
- This 407Mi of residual memory was never reclaimed despite all dashboard CRs being removed

This means back-to-back dashboard creation/deletion cycles will accumulate memory until OOMKill, regardless of the per-run dashboard count. A clean test would require restarting the perses-operator pod between runs to reset its memory baseline.

### Memory Scaling Estimate

From the clean-baseline runs (Run 2 and Run 4):

| Dashboards | Baseline | Post-Load | Delta | Per-Dashboard Cost |
|---|---|---|---|---|
| 2,000 | 24Mi | 492Mi | 468Mi | ~0.23 Mi/dashboard |
| 800 | 15Mi | 328Mi | 313Mi | ~0.39 Mi/dashboard |

The per-dashboard memory cost is not linear — it's higher at lower counts (likely fixed overhead). With the 512Mi limit and ~15Mi clean baseline, the operator can safely handle approximately **800–1,000 dashboards** before approaching OOMKill territory. At 2,000+ dashboards, OOMKill is expected.

### Conclusions

1. **800 dashboards across 100 namespaces is the approximate safe threshold** for the current 512Mi limit — the operator reaches 328Mi (64% of limit) with no OOMKills.
2. **At ~1,000+ dashboards the perses-operator OOMKills** — confirmed on two separate clusters (Run 0 on 05-27, Run 2 on 06-02).
3. **The perses-operator memory request (128Mi) is undersized** for any meaningful dashboard workload. Even 800 dashboards results in 2.5x the request.
4. **Memory is not released after dashboard deletion** — restarting the operator pod between dashboard lifecycle events is required to avoid cumulative memory growth.
5. **For workloads exceeding ~1,000 dashboards**, the memory limit needs to be increased (recommend 1Gi) or the perses-operator needs a memory leak fix.
